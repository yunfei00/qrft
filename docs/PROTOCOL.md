# QRFT 二维码协议：v1 兼容与 v2 HEX + MD5

## 当前单机入口补充（2026-10-15）

`python -m qrft decode 项目目录` 仅解析已有 V2 / QRFT2100，不新增 v1 兼容逻辑。当前独立编码器 START 是 `文件名,实际传输MD5,总包数,QRFT2100`、分块 2100、控制帧各一次，冻结规范见 [ENCODER_2100_PROTOCOL.md](ENCODER_2100_PROTOCOL.md)。下方 1400 字节/控制帧 20 次描述属于旧 V2，仍按其真实 START 识别，不能与 QRFT2100 混任务。

两种协议均无线上文件大小和文件 ID，单机项目按首次有效 START 的完整元数据锁定；task_id 是内部派生标识，大小由整块和末块推导。目录 START MD5 保持实际 ZIP 字节 MD5，ZIP comment 的 Folder Content MD5/SHA256 单独流式验证。没有修改任何已发布帧格式；既有 v1 实现和依赖保留。项目恢复与限制见 [单机手册](SINGLE_DECODER_USER_GUIDE.md)。

更新日期：2026-10-12。v2 按本次确认格式实现，所有额外的 version/file_size/SHA256 都是内部状态或离线信息，**不会插入 v2 帧**。开发分支 feature/qrft-v2-hex-md5，软件版本 0.4.0.dev0；旧 0.3.0rc1 Release 不支持 v2，本轮不合并、不发布。

## v2 唯一线格式

```text
CONTENT_HEX + CONTENT_MD5_HEX + PACKET_ID_HEX
```

无分隔符、头部或额外字段。三段全部大写 HEX；正文为原始字节的 HEX，MD5 是原始正文的 MD5（32 字符，不能再 HEX 编码），编号先格式化为 8 位十进制 ASCII，再对这 8 字节 HEX 编码（16 字符）。从尾部逆向切分 16、32、剩余字符，严格验证大写 HEX、偶数长度、八位 ASCII 数字及正文 MD5。错误帧丢弃并记录视频帧号与原因。

| 编号 | ASCII 的 HEX |
|---|---|
| 00000001 | 3030303030303031 |
| 88888888 | 3838383838383838 |
| 99999999 | 3939393939393939 |

### START

编号 88888888，正文 UTF-8：`文件名,文件MD5,总块数`。文件 MD5 为整个原文件的 32 位大写 HEX。文件名可以含逗号，从右分割最后两个字段；总块数为非负十进制整数，空文件为 0。START 正文自身独立计算 MD5。重复元数据幂等；文件名、文件 MD5 或总块数不同则拒绝绑定同一任务。

### DATA

原文件固定 **1400 字节**分块，末块保留实际长度、不填充。编号从 00000000 连续递增，最大 88888887（不进入保留号）。每块正文独立 MD5。非末块必须恰好 1400 字节，末块为 1–1400 字节，空文件没有 DATA。同编号同内容去重；不同有效内容持久化到冲突表、不覆盖原包，v2 有冲突时拒绝发布文件，需新建隔离任务排查来源。

### FINISH

编号 99999999，正文严格为小写 `finish` 的 UTF-8 字节。FINISH 仅记录发送结束，不能据此判定恢复成功。v2 在已绑定 START、包完整且整个文件 MD5 一致时可以恢复，即使 FINISH 因录屏截断未识别；v1 继续保留其原先需要 FINISH 的恢复条件。

### 完整字段示例

DATA 编号 1，原始正文两字节 00 FF（按内容 HEX / MD5 HEX / 编号 HEX 分行展示，线上直接拼接）：

```text
00FF
D07D34EFAC6328007AD67C7E0A985E00
3030303030303031
```

完整 FINISH：

```text
66696E6973683248BC7547CE97B2A197B2A06CF7283D3939393939393939
```

## 二维码与播放

`qrcode.QRCode(version=None, error_correction=ERROR_CORRECT_L, box_size=10, border=4)`；添加大写 HEX **文本**，保留库的自动数据模式选择，`make(fit=True)`。PIL RGB 转 OpenCV BGR，用 `INTER_NEAREST` 缩放 50%。CLI OpenCV 路径使用 `imshow()`/`waitKey()`，Qt 与 PNG 导出共享相同渲染核心。Qt 根据 DPI 映射图像像素，窗口空间不足时明确失败，不裁切二维码或缩小到错误参数。

START 连续 20 次，每次 50ms；DATA 每包一次，默认 50ms；FINISH 连续 20 次，每次 50ms。PNG 导出只保存每种控制帧一张，播放及视频生成按上述次数复用，避免重复文件。预生成缓存有界，不载入整个文件。50ms 是调度间隔，二维码生成、Windows 调度及暂停可能延长实际展示；不能宣称实机恒定20fps。生成测试 AVI 则明确为20fps固定帧序列。

1400 字节随机正文为 2848 字符，已实际生成 QR version33、缩放后785×785，通过 ZXing 字节精确往返。自动模式可能随内容选择不同版本，不能依靠硬编码版本。超长文件名 START 触发库的容量/版本超限时明确报错，不截断或修改分块参数。建议原生1080p及以上显示器，录制完整四周留白。

## 恢复、补传与任务隔离

本地恢复输出目录就是一个明确任务；`.qrft-session/receipts.sqlite3` 保存原始帧、START、FINISH、协议锁及冲突。多个视频必须显式指定同一任务目录；中断后的已确认帧保留。先收到 DATA、后收到 START 可验证并绑定；没有 START 时不能知道文件归属和总块数，等待 START、不发布文件。

控制中心新建任务必须选 v2（API `POST /tasks` 的 `protocol_version:2`）；旧客户端不传时仍为 v1，旧数据库任务迁移为 v1。登记视频必须提供 task_id，Worker 领取租约后直接扫描所绑定视频、保留扫描的原始线帧提交。HTTP API的Base64仅为传输封装，不是二维码字段，解包后仍是完全相同的三段HEX原始帧。协议一经确定不能切换，v1/v2 混用返回错误；时间片没有 START 仍能向明确的 v2 任务提交合法 DATA，等待其他节点提供 START。

v2 DATA 没有文件 ID，帧 MD5 不能证明来自哪个文件。必须由用户或验收器将原视频及同文件补传明确关联到同一任务，未知归属不得自动混入。START 一致性、冲突隔离和最终文件 MD5 是一致性检查；**MD5 不是防恶意篡改的安全认证机制**。API Token 鉴权继续保留。

按 START 总块数和已收包计算 TXT/CSV/JSON 缺包列表，`missing.txt` 每行原始八位包号或闭区间。补传必须使用未改变的原文件、1400 字节分块、原包号和原内容；补传再次带20次 START 和20次 FINISH。恢复按包号流式写入临时文件，从末包确定长度，完整 MD5 匹配才原子发布到 `files/文件名`，已有用户文件不能覆盖。v2 无线文件大小或 SHA256；恢复 API 可额外返回本地计算 SHA256，但不将它冒充 START 中的期望值。

## v1 线格式原样保留

```text
DATA   = 原始数据 || CRC32(大端4字节) || 8位ASCII包号
START  = QRFT1S || UTF-8紧凑JSON || CRC32 || 88888888
FINISH = QRFT1F || CRC32 || 99999999
```

CRC32 范围为正文与八位 ASCII 编号，START 含原文件大小、分块、MD5、SHA256、file_id。v1 二维码仍使用 Byte 模式及原可配置参数，编码默认继续为 v1；解码严格验证 v1 CRC 或 v2 HEX/MD5，任务层再验证版本。现有 v1 测试与冻结程序验收继续执行。

## 验证边界

自动生成20fps MJPG AVI、Qt事件测试和本地两个独立 Worker 都是自动化软件验证，不等于 Windows11 实际 MP4 录屏或双机 SMB。真实步骤见 USER_ACTIONS.md 的 UA-009；原里程碑仍7/10。
