## 二、执行安全和资源上限（不可跳过）

1. 先执行 `git status`、`git rev-parse HEAD`、`git fetch` 并记录源码版本及是否有本地修改。**绝不 reset/clean/强推，也不覆盖用户未提交修改。** 工作树不干净需保护现场，在受控独立工作目录操作，不能直接删除或覆盖。
2. 所有测试使用独占工作目录（建议 `temp/p10-<uuid>`），增加 `OWNER.txt` 所有权标记。不得使用/清理 P8/P9 用户的手工录像、已有任务工作区、系统临时目录或生产数据。任何删除必须严格限制在本轮新建且已验证归属的目录，不默认自动清理以免丢失证据。
3. 启动前采集 CPU/内存/空闲磁盘/版本/依赖/视频编码器情况，估算二维码包数、帧数、生成时间和所需空间；运行中连续检查空闲空间、峰值 RSS 和耗时。**必须有可重复的资源保护程序**：如果剩余空间可能低于 8 GiB 或当前可用空间的 20%（取较大值），停止创建更大视频；运行日志不得暴露 Token 或私有视频。
4. 默认 P10 运行总时长预算约 2 小时；单项工作负载建议设置 30 分钟超时并可中断保存报告。时间预算可随设备能力下调；超时要明确标记 `BLOCKED_BY_LIMIT` / `NOT RUN` 而非伪造 PASS。不能为了满足规模目标不受控地占满磁盘或内存。
5. 建议本轮合成视频产生的数据总量上限为 15 GiB，实际以更严格的空闲空间保障为准。高风险、估算超限的用例保留设计和估算表，不直接运行。**严禁直接生成 1 GiB 数据的完整二维码序列或无界大视频。**
6. 外部第二台 Windows / SMB 真正断网重连，只有设备和共享资源实际可用才验收；否则明确标记 `NOT TESTED - requires second physical host`，不得使用两进程冒充双机。
7. 对性能测试减少人工录屏需求，可使用编码核心生成真实可解码合成 MP4；须明示它不是 Windows 截图工具录屏。已有用户录像只能在授权且实际可访问时只读复用，不能凭假定路径编造证据。
8. 如果当前 Codex 执行环境无法持续运行原生 Windows GUI，则让能运行 GUI 的 Codex 本地环境执行；不能把 offscreen/headless 冒充原生窗口验收。CI 不足以替代现场长时间 GUI 的测试。

## 三、分层测试矩阵（由低到高，不一次跑大规模）

| 层级 | 负载 | 实施要求 | 通过标准 |
| --- | --- | --- | --- |
| P10-A 基线 | 64 KiB 合成 MP4 | 使用现有 `scripts/decoder_benchmark.py`，1/2/4 个**独立系统进程** Worker，尽可能每档重复 3 次；生成一次素材并复用同一视频、相同 slice 配置做公平比较 | 字节、MD5/SHA256 一致，无冲突/缺包，记录每次扫描耗时、包/s、资源、视频时长与重复数 |
| P10-B 中等文件 | 1 MiB | 完整 编码→合成 MP4→解码→恢复 链路，测试 1/2/4 Worker；优先复用视频素材，记录性能中位数和波动 | 没有任务丢失、没有假完成、最终字节和哈希一致，工作区退出可重新打开 |
| P10-C 较大文件 | 10 MiB | **先估计**所需包数/帧数/时长/磁盘占用；资源满足时至少一档 Worker 跑完整链路，并在长任务中验证暂停/恢复或 Worker 异常重领；如果估算超过资源预算，明确 `NOT RUN` 并保留估算和最接近的实测 | 被执行的样本须完整恢复、哈希匹配，时长/吞吐/资源如实记录 |
| P10-D 大规模 | 50–100 MiB | **条件执行，不默认生成视频**；可先做模拟包存储/报告/流式恢复的真 SQLite 大规模测试，与真实视频链路严格区分；只有测算后不触发内存/磁盘/时间上限时才做完整视频 | 真实运行什么就记录什么；不得把纯数据库/哈希压测说成二维码视频解码通过 |
| P10-E 1 GiB | 仅结构/存储/恢复压力 | 默认只做受控容量估算及磁盘包仓库/哈希机制边界测试；**不生成 1 GiB 完整二维码视频** | 记录容量限制、估算视频时长、需用存储；完整 1 GiB QR 链路标注 `NOT TESTED` |

说明：Worker 吞吐提速不是“必须 > 1”，原因包括 SQLite 写入、视频解码、时间片长度及磁盘 I/O 的竞争。必须同时报告加速比 `T(1 worker)/T(N workers)` 和增加的 CPU/RSS/磁盘开销；不能删去反向变慢的数据。

## 四、长时间与故障回归

1. **长时运行与内存稳定性**：在正常 Windows 原生 GUI 或真实 Control/Worker 组合中执行至少 10 分钟受控负载，记录 RSS（起始/峰值/结束）、CPU、I/O、活动进程数量、日志错误、心跳和时间片进度；若设备空闲、资源余量和预算允许，再扩展 30 分钟，60 分钟仅在可控环境中按独立运行继续。仅将实际完成的时长写 PASS，不把短视频反复刷新伪称长视频解码。GUI 挂机稳定性与长视频识别性能分开记。
2. **中途故障**：在任务有活动时间片时结束一个 Worker，验证租约过期被其他真实进程接管；暂停/继续、Cancel/Resume、重启本地 Control 和 GUI、重新连接、持久化数据不丢、重领不出现重复破坏。
3. **受限或不正常输入**：破损 MP4、无 START、有 START 但缺包、缺 FINISH、同包不同内容、视频切片边界/重叠、错误 MD5、不可写输出目录、剩余空间不足预警；必须拒绝把不完整任务算作恢复成功，不得覆盖已经存在的结果。
4. **数据库耐久性**：SQLite `integrity_check`、冲突隔离、重复包幂等、报告导出，尤其是大规模包表和关闭后再次恢复；测量数据库增长、索引查询速度及内存。
5. **单机 N Worker**：1、2、4 进程要有不同 node_id、不同 slice 的实际处理证明；记录在一个共享视频上并行工作的边界和收益，不以进程数量或任务创建数量代替真实吞吐证明。
6. 任何测试不得改变既有 v2 格式（大写 HEX、1400 字节、MD5、START/FINISH）或 P8 GUI/CLI 口令行为；保持 v1 原协议兼容。
